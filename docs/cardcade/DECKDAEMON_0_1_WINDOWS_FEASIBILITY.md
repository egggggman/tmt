## 0.1 minimal feature contract

**Single purpose:** Browse preserved, local, already-existing project evidence on Windows. A **view** is not an engine state transition.

1. **Source identity / startup screen:** selected snapshot root, exact reviewed manifest identity and digest if supplied, display file provenance, explicit “INSPECTION ONLY — NO GAMEPLAY” label. If `git` is unavailable in a packaged distribution, do not invent a Git SHA; show “unverified source” unless independently supplied by a validated, immutable packaging manifest.
2. **Deck browser:** discover only manifest/explicitly allowlisted text files under `decks/`; show character/deck name, exact relative path, preserved prototype version text and raw content. Parsing card totals may be introduced later after format tests; don't silently infer Standard legality.
3. **Baseline 005 report viewer:** show `OBL_BASELINE_005_MANIFEST.json` identity, immutable contents and historical per-deck metrics/matchup grid with clearly attributed “Historical Baseline 005” labeling. No live claims and no simulated results generated by the UI.
4. **Diagnostic evidence browser:** only allowlist previously verified JSON/text report paths after a separate fixture inventory and content/schema audit. Show explicit source SHA, diagnostic status, stop records and unsupported-semantic warnings when present. Files absent or not approved display “not available”; never replace missing evidence with fabricated data.
5. **Read-only diagnostics:** missing-file, invalid JSON, hash mismatch, schema mismatch, file too large, or malformed path must display a visible failure and refuse to mark data verified.

**Explicit exclusions:** Run Match, Continue, Retry, Seed/Deck controls that generate gameplay, simulation imports, driver controls, real signed permits, approval/claim creation, network reads, database initialization/migration/queries with writes, deck editing, calibration, result promotion, archive writes, code execution in user-supplied content, shell/process controls, hidden auto-repair, tool/workflow triggering. If a future mock button would imply “Play,” omit it entirely.

## Proposed architecture / trust boundaries

```text
Windows user
  |
  v
DECKDAEMON viewer (Tkinter/ttk; no execution controls)
  |  [pure functions: resolve allowlisted paths; read bounded UTF-8/JSON;
  |   hash bytes; validate minimum schema; present declared provenance]
  v
Explicitly designated local SNAPSHOT ROOT (read-only, finite allowlist)
  |-- decks/*/PROTOTYPE_0.1.txt and explicitly approved prototype paths
  |-- docs/objective-balance-lab/baselines/OBL_BASELINE_005_MANIFEST.json
  |-- approved archived report fixtures only
  X-- no engine07/stage002 imports or executable diagnostic launcher
  X-- no writes to repository, archive, claims, decks, or authorizations
```

**Packaging recommendation:** separate `deckdaemon_viewer` package/module (future; no dependency on `tmnt_design_studio.engine07`, `stage002`, `tools/cardcade_diagnostic_launcher.py`, `subprocess` or `socket`) and a clearly named `deckdaemon-inspect` launch target, not the current `tmnt` CLI. A static data reader must use a strict allowlist, fixed per-file byte limits, UTF-8 JSON/text only, reject symlinks and path traversal, resolve and verify all paths remain under the designated snapshot root, and verify expected digest/provenance where available. Keep all display content escaped/plain text (not executed as HTML/scripts).

**Critical distinction:** a UI with no action buttons is *not itself an OS sandbox*. A user who can modify the repository or its saved evidence can change what is displayed unless immutable input hashes/provenance are checked. The GUI must not describe that as verified evidence. Avoid directory crawling or unrestricted file-open dialogs in 0.1. Do not bundle signing keys or private card data.

**Installation layout:** use a frozen read-only artifact snapshot bundled with a later Windows distribution or a separately designated version-pinned snapshot. Do **not** point the release to a mutable working checkout by default. The initial Python prototype may use an explicitly provided local test root with deterministic fixtures.

## Minimal verification plan (future authorization needed for build)

**Gate A — inspection data contract (without GUI):**
- Designate an exact input fixture list and digest table; confirm all paths exist and parse without mutation.
- Pure reader tests: known valid manifest and deck file; file missing; bad JSON; wrong digest; symlink or `..` traversal; oversized file; malformed manifest; inaccessible directory. Verify no reads outside allowlist and no filesystem changes.
- Validate all intended views use only approved fixture values and label Baseline 005 as historical.

**Gate B — Python UI smoke (inspection-only):**
- Native Windows launch, open/read/close, error dialogs, keyboard navigation, scaling/readability and no uncaught exceptions.
- Instrument/spy on `open`, imports, subprocess/network, and filesystem writes where feasible. Never call the Cardcade engine, diagnostic launcher or any run wrapper.
- Confirm none of the UI controls mutate filesystem or trigger a game.

**Gate C — packaging proof (not yet authorized):**
- Pin the chosen packager version; build **one-folder** Windows proof in isolated location with offline locked inputs; record build OS/Python versions, full command, resulting EXE hash, bundled files and license notices.
- Start it on a clean Windows account without Python and verify fixture provenance, accessibility, error paths, no network, no write outside temporary OS-managed runtime locations; repeat with files missing/tampered.
- Confirm package includes no real signing material, run authorizations, mutable cards/decks, hidden CI dispatch or embedded pilot runner. Release and installer signing are separate later decisions.
