## Closure order

1. **Menace / multiple blockers** — establish combat legality and allocation first because it changes the option domain used by several other combat families.
2. **Leonardo graveyard casting + finality** — establish graveyard authority, alternate casting, incarnation identity, entry replacement and death replacement as one lifecycle.
3. **Paramecia death / exile / reflexive return** — reuse authoritative death and incarnation lineage from the Leonardo lifecycle, but keep its optional choice and target transaction distinct.
4. **Raphael linked exile + attack-time play** — reuse source-linked exile and permission-lifetime primitives after zone/identity work is accepted.
5. **Ooze Spill counterspell / Mutagen** — reuse mature instant, Stack/Priority and token activation/payment primitives; validate the compound transaction last because it crosses response and token surfaces.

This order is a dependency proposal, not implementation authorization. Each family needs a separate HQ scope decision and acceptance packet.

## Cross-family dependencies

- Combat legality (Menace) is foundational for any family whose outcomes use attack/block survival, including Raphael attack-time play and Ooze token combat consequences.
- Zone/incarnation lineage and replacement handling (Leonardo) is reusable for Paramecia death and Raphael source-linked exile, but each card's optional choices remain separate acceptance surfaces.
- Stack/Priority and payment infrastructure is shared by Leonardo casting and Ooze Spill; acceptance must show source-specific legality rather than generic activation success.
- Token identity, sorcery timing and counter replacement affect Ooze Spill and deferred Michelangelo/Frog interactions; do not let a generic token event stand in for Mutagen semantics.
- Pilot observation/privacy and decision ownership are protocol dependencies. Semantic implementation cannot silently add hidden-zone information or new chooser responsibility.

## Per-family acceptance gate

Each implementation packet must include exact Oracle/card identity and source hashes; an explicit state/lifecycle diagram; legal and illegal option fixtures; deterministic duplicate replays; seat/ID/option-order transforms; authoritative Action/event/Stack/Priority/zone/lineage evidence; invariant and terminal tests; applicability/unsupported classifications; and a result audit that reconstructs claims from raw evidence. A family is not closed by a parser match, a generic event, a single successful witness, or a changed coverage label.

Release to the accepted Calibration Protocol requires all five families to be accepted or an explicitly reaccepted protocol scope that excludes them. The four deferred risks require individual applicability dispositions. The future release addendum must freeze the resulting engine, Pilot, runner, analyzer, catalog, decks, dependencies, seed table and storage capacity before any seed generation or gameplay.
