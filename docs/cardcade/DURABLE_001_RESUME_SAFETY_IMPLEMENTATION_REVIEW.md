## Authority boundary

`ReviewLease` is a trusted, single-use **in-process synthetic test capability**.
It is not an authorization file parser or an issuer of HQ authority. It requires
900 synthetic-marked schedule rows, a 732-record reference, exact byte hashes,
the complete schedule digest, source/input hashes, actual imported project paths,
the current interpreter hash and the supported status protocol. Live mode is
explicitly refused. The Durable CLI no longer has a default simulator executor
or a missing-file new-run fallback; it cannot mint a lease from CLI arguments.

The original 49-file seal remains an audit reference. New source hashes identify
this fork and do not relabel it as the frozen producer. Unavailable historical
interpreter/startup/editable-install evidence is not inferred or excepted.

The reference and working checkpoint must be different, non-hardlinked,
non-reparse paths in different directories. Neither library writes the reference.
Source manifests cover all runtime Python files and existing launcher/provenance
and monitor entrypoints; foreign imported project modules fail verification.

## Ownership and continuation

The resume path holds canonical checkpoint and control-store ownership markers
through validation, restore and commits. Optional retained OS-backed marker locks
are enabled for this path: Windows byte-range locking / POSIX flock. Stale markers
fail closed. There is no automatic ownership theft, evidence repair or cleanup
policy for an interrupted run. Cooperative ownership still needs trusted ACLs.

Receipts are exclusive-create, flushed/fsynced, append-only HMAC-SHA256 events.
The receipt key must be supplied independently by the trusted test authority;
it is never read from checkpoint/status files or written into receipts. Only
test fixtures contain test keys. The policy binds working/reference/control paths,
source/input/interpreter identity and schedule.

Each successor has START (prior checkpoint/count and next ID), PREPARE (the hash
of the actual flushed temporary file), and COMMIT (persisted file hash/count and
record hash). PREPARE is generated by a callback in the reused #365 writer just
before replacement. The persisted hash must equal PREPARE before COMMIT. No retry
budget is increased. A failed receipt callback cannot replace the checkpoint.

At first entry the exact initial bytes and 732-record prefix are required. For a
continuation, a **new independently issued test lease** must pin the latest receipt
tip. All receipt MACs, predecessor links, phases, counts, original records and
subsequent record hashes are verified. The current checkpoint must equal the
committed hash and exact schedule prefix. Completed IDs are skipped by position;
only the next authorized row can be dispatched. A stale initial lease cannot
overwrite later progress while the trusted receipt head remains enforced.

Any START/PREPARE without COMMIT, malformed/conflicting/missing receipt, wrong
tip, or changed checkpoint blocks another invocation. A failed process cannot
renew its own lease. No guessed rollback or automatic adoption is implemented.
Checkpoint replacement and receipt persistence are not one atomic transaction;
ambiguity is handled by stopping and preserving evidence. Power-loss durability
requires additional target-host testing, not an inference from fsync alone.

**Trust limit:** HMAC chains do not detect complete rollback when both history
and its supposed trust anchor are attacker-controlled. The latest tip and key
must come from an independent trusted authority. The live issuer, protected
durable anti-rollback store, expiration/revocation/session policy and permission
verification are not selected or enabled by this draft. A caller must not treat
arbitrary serialized `ReviewLease` fields as authenticated authority.

## Status-only monitoring

`scripts/durable_status_monitor.py` accepts only a status path and authorization
ID. There is no checkpoint option. The status filename must be
`durable-status.json`; reparse/hardlink aliases are rejected. The reader opens
read-only, non-inheritable, with Windows read/write/delete sharing, reads at most
4097 bytes to enforce the 4096-byte limit, and closes before parsing/sending.
It never tails or retains a checkpoint stream.

A spawned read worker is supervised with a 250 ms deadline including startup;
timeout causes termination and join. OS scheduling is not a hard real-time
guarantee. Slow or malformed/oversized/stale/future/foreign/unsupported telemetry
returns UNKNOWN. Valid telemetry is always REPORTED_ONLY, never authenticated
checkpoint evidence or resume authority. A payload cannot override that label.

Status publication follows a committed checkpoint/receipt in a separate directory.
A held status reader can deny status replacement, but cannot hold the checkpoint
path. Publication failure stops before another dispatch; the already committed
checkpoint and receipt remain valid and require renewed authority to continue.
No production monitor or PowerShell policy is changed. The older direct-checkpoint
monitor is incompatible and is not silently redirected or deployed.

The live monitor token/ACL separation, code-version pin and startup handshake
remain mandatory operational acceptance work. This draft does not claim that a
filename/protocol check substitutes for those controls or excludes privileged
third-party readers. The live adapter remains disabled until those requirements
and the independent exact-identity governance gate are resolved explicitly.
